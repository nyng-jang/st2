# 과제 8 · 패스키(WebAuthn) 인증 구현 설명서

- 결과물 URL: https://st2-six.vercel.app (첫 화면은 누구나 보는 공개 소개 페이지)
- 비공개 영역: https://st2-six.vercel.app/private.html (패스키로 로그인한 본인만 내용이 보임)
- 소스 URL: https://github.com/nyng-jang/st2
- 증거 기록: [docs/evidence/](evidence/) 의 요청·응답 기록

> 비공개 영역의 내용, 계정 이름(demo-a, demo-b, test-a, test-b), 메모는 모두 직접 지어낸 가상 자료입니다. 연락처·신분증 번호 같은 실제 개인정보와 비밀값은 저장소 어디에도 없습니다. DB 접속 주소는 Vercel 환경변수에만 있습니다.

## 짧은 확인 방법

1. **어디로 가나요**: https://st2-six.vercel.app 를 새 시크릿 창에서 엽니다.
2. **세 단계 안에 무엇을 하나요**: ① 첫 화면 공개 소개를 끝까지 내려 "여기까지 공개 영역 · 아래부터 비공개 영역" 경계를 봅니다 → ② "비공개 영역으로 가기"를 누릅니다 → ③ 주소창에 `https://st2-six.vercel.app/api/private` 를 직접 엽니다.
3. **무엇이 보이면 통과인가요**: 공개 소개는 그대로 보이고, 비공개 영역에는 로그인 버튼만 있고 메모가 없으며, ③은 `401` 과 `{"error":"not_authenticated"}` 입니다.
4. **안 될 때는 무엇이 보이나요**: 비공개 영역에 "[가상]" 메모가 보이거나 ③이 `200` 으로 자료를 돌려주면 실패입니다. 서버가 멈췄을 때는 ③이 `500` 으로 보입니다.

## ① 무엇으로 붙였나

- **라이브러리**: 서버 검증에 [SimpleWebAuthn](https://simplewebauthn.dev/) `@simplewebauthn/server` 14.0.3 을 썼습니다. 브라우저 쪽은 라이브러리 없이 표준 `navigator.credentials.create()` / `get()` 을 직접 불렀습니다.
- **서버**: Vercel 서버리스 함수(Node.js), `api/` 폴더.
- **저장소**: Supabase Postgres 의 `passkey` 스키마. 앱은 이 스키마에만 권한이 있는 `passkey_app` 역할로 접속합니다.
- **인증 서비스(Auth0, Supabase Auth 등)는 쓰지 않았습니다.** 챌린지 보관, 서명 검증 결과 처리, 세션은 직접 구현했습니다.

## ② 왜 그걸 골랐나

- 서명 검증(CBOR·COSE 해석, rpIdHash·origin·카운터 확인)은 직접 짜면 틀리기 쉬워서 검증된 라이브러리에 맡겼습니다.
- 대신 과제의 핵심인 **일회용 챌린지 보관과 소비, 계정 분리, 세션**은 직접 짜서 코드에서 흐름이 보이게 했습니다.
- 인증 서비스를 쓰면 챌린지와 공개키 저장이 서비스 안에 숨어서 "서버에 무엇이 저장되는지" 보여 주기 어렵습니다.
- 과제 1 페이지가 이미 Vercel 정적 배포라서, 같은 프로젝트에 함수만 더하면 공개 페이지를 건드리지 않고 붙일 수 있습니다.

## ③ 어디를 어떻게 고쳤나

공개 페이지(`index.html`)는 메뉴에 "비공개 영역 🔒" 링크와, 본문 끝의 공개·비공개 경계 카드만 더했습니다. 과제 1 공개 내용은 그대로입니다.

| 흐름 | 지나는 소스 |
| --- | --- |
| 등록 | `private.html` `register()` → `api/register/options.js` (챌린지 생성 23행, 서버 보관 34행) → 브라우저 `navigator.credentials.create()` → `api/register/verify.js` (챌린지 소비 11행, 서명·공개키 검증 26행, 공개키 저장 41행) |
| 로그인 | `private.html` `login()` → `api/login/options.js` (새 챌린지 20행, 보관 25행) → `navigator.credentials.get()` → `api/login/verify.js` (챌린지 소비 12행, 삭제된 패스키 거절 16행, 다른 계정 패스키 거절 18행, 공개키로 서명 검증 24행, 세션 발급 45행) |
| 로그아웃 | `private.html` 로그아웃 버튼 → `api/logout.js` 6행 → `lib/auth.js` `endSession()` 80행 (DB 세션 행 삭제, 쿠키 만료) |
| 비공개 자료 조회 | `private.html` `refresh()` → `api/private.js` 7행 `requireAccount()` (`lib/auth.js` 65행, 세션 없으면 401) → 세션 계정 자료만 조회 |
| 다른 계정 자료 거절 | `api/accounts/[id]/private.js` 10행 (403), `api/private.js` 는 주소·본문의 계정을 무시 |
| 패스키 목록·삭제 | `api/passkeys.js` (남의 패스키 삭제 403은 34행, 마지막 패스키 삭제 409는 41행) |
| 챌린지 일회성 | `lib/auth.js` `consumeChallenge()` 95행: `delete ... returning` 으로 꺼내면서 지움. 유효 시간 5분(`CHALLENGE_TTL_SECONDS`) |
| DB 구조 | `db/schema.sql`, 가상 자료 `db/seed.sql`, 앱 역할 권한 `db/roles.sql` |

**로그인 후 사용자 식별 방식: 서버 세션.** 로그인에 성공하면 32바이트 무작위 토큰을 `sid` 쿠키(HttpOnly, Secure, SameSite=Strict, 1시간)로 주고, DB에는 그 SHA-256 해시만 저장합니다. 요청마다 쿠키 해시로 계정을 찾습니다. 로그아웃하면 DB 행을 지우므로 같은 쿠키를 다시 보내도 401 입니다.

**서버에 저장되는 값 (비밀번호가 아니라 공개키).** `passkey.credentials` 한 행에는 자격 증명 ID, COSE 형식 공개키, 서명 카운터, 전송 방식, 이름, 등록일만 들어갑니다. 공개키는 이름 그대로 공개돼도 되는 값이라, 이것만으로는 로그인할 수 없습니다. 로그인하려면 인증기 안의 개인키로 서버의 새 챌린지에 서명해야 합니다. 실제 저장된 값은 [증거 기록](evidence/)의 "서버에 저장된 공개키" 절에 있습니다.

**패스키를 저장한 곳 (실기기, 2026-11-19 직접 확인)**: demo-a 의 첫 패스키 "아이폰15" 는 아이폰의 **iCloud 키체인**에 저장했습니다(서버 기록상 동기화형 `multiDevice`, 백업됨 `true`). 두 번째 패스키 "Chrome" 은 아이폰에서 **Chrome(구글 비밀번호 관리자)** 를 저장 위치로 골라 등록했습니다. 서로 다른 저장소 두 곳입니다. 참고로 처음에 PC Chrome(구글 비밀번호 관리자)으로 만든 패스키는 PC에서 두 번째 저장소를 쓸 수 없어 지우고 아이폰으로 다시 시작했습니다.

**실기기 확인 (T08-C42~C45)**: 12:27 "아이폰15" 등록 → 12:33 "Chrome" 추가(목록에 2개) → "Chrome" 삭제 → 남은 "아이폰15" 패스키로 로그인(12:34)해 비공개 자료 3건 확인, 목록은 1개. 삭제한 "Chrome" 패스키로는 서버가 자격 증명을 찾지 못해 거절합니다(자동 기록의 `unknown_credential` 401 과 같은 동작). 화면 캡처: [로그인 후 비공개 자료](evidence/real-device/2026-11-19-login-iphone15.png), [삭제 후 패스키 목록(1개)](evidence/real-device/2026-11-19-passkey-list-after-delete.png).

**패스키가 하나도 남지 않으면**: 마지막 패스키는 삭제를 막았습니다(409, 화면 안내 "마지막 패스키는 지울 수 없어요"). 만약 기기 쪽에서 패스키를 잃어 쓸 수 있는 것이 0개가 되면 그 계정으로는 다시 들어갈 방법이 없습니다. 이 때문에 두 개 이상 등록을 화면에서 권합니다.

## ④ 안 열리는 것을 확인한 기록

자세한 요청·응답은 [docs/evidence/](evidence/) 에 있습니다. 세션 쿠키 값은 가렸습니다.

| 확인 | 통과한 요청 | 거절된 요청 |
| --- | --- | --- |
| 로그인 없이 열기 | 로그인 후 `GET /api/private` → 200, 내 자료 3건 | 로그인 없이 `GET /api/private` → **401** `not_authenticated` |
| 남의 패스키로 열기 | test-a 세션으로 `GET /api/private?account=test-b` → 200, test-a 자료만 | test-a 세션으로 `GET /api/accounts/test-b/private` → **403**, 반대 방향도 **403**, test-b 패스키로 test-a 로그인 → **401** `credential_account_mismatch` |
| 사용한 챌린지 재사용 | 새 챌린지로 서명한 응답 → 200 | 같은 응답을 한 번 더 → **400** `challenge_invalid` |
| 패스키 삭제 뒤 로그인 | 남은 두 번째 패스키 → 200 | 지운 첫 번째 패스키 → **401** `unknown_credential` |

## ⑤ AI와 나

- **AI에게 맡긴 일**: 서버 함수·비공개 화면 코드 작성, DB 스키마, 가상 인증기로 요청·응답을 기록하는 스크립트, 이 설명서 초안.
- **내가 직접 판단한 일**: 과제 1 원본을 어느 저장소로 할지, 직무 관련 문구와 실제 서류 스캔을 뺀 것, 비공개 자료를 모두 가상으로 채운 것, 실제 기기로 패스키를 등록할 저장 위치.
- **AI 제안을 따르지 않은 일**: AI는 처음에 `portfolio` 저장소를 과제 1 원본으로 짐작해 거기에 붙이자고 했지만, 실제 과제 1 제출물은 `st2` 였으므로 st2에 붙였습니다.

## ⑥ 아직 못 막은 것

1. **요청 횟수 제한이 없습니다.** `/api/login/options` 를 계속 부르면 챌린지 행이 쌓입니다. 만료된 것은 다음 검증 때 지우지만, 짧은 시간에 대량 호출하는 것은 막지 못합니다.
2. **첫 등록 시점의 빈틈.** 패스키가 0개인 가상 계정에는 누구든 먼저 첫 패스키를 등록할 수 있습니다. 실제 서비스라면 이메일 확인이나 초대 링크로 첫 등록을 묶어야 합니다.
3. **세션 쿠키를 빼앗기면** 만료(1시간) 전까지 그대로 쓸 수 있습니다. 기기·IP에 묶지 않았습니다.
4. **attestation 을 `none` 으로 받아** 인증기 제조사·종류를 검증하지 않습니다. 어떤 인증기든 등록됩니다.
5. **모든 패스키를 잃으면 복구 수단이 없습니다.** 마지막 하나의 삭제만 막았을 뿐입니다.
